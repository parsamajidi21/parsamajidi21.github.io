Neural Network Implementation on FPGA using HLS

Created on December 02, 2024

2024   ·   AI   FPGA   ·   AI-Acceleration

TL;DR: I trained a small fully connected network in Keras, converted it to fixed-point FPGA firmware with hls4ml, and integrated the generated IP on an Arty A7-100T together with a hand-written VHDL UART and FIFO. The firmware keeps 74.9% accuracy (vs. 76.4% in floating point), and synthesis estimates a latency of ~178 clock cycles with a new inference accepted every 32 cycles.

Code: github.com/parsamajidi21/DNN-FPGA

Introduction

There are two ways to put a neural network on an FPGA:

  1. Write the whole network in VHDL. You design a single neuron, instantiate one for every node in the network, and route all the signals between them by hand. You stay in full control, but even a small network turns into a lot of RTL.
  2. Use a high-level flow such as hls4ml. You start from the same Python model you used for training. hls4ml translates it into HLS C++, and Vivado HLS turns that into an IP core you can instantiate in a VHDL design.

The first option means writing much more VHDL; the second means trusting a tool. I went with hls4ml for the network itself and wrote the I/O around it (UART, FIFO, top level) by hand in VHDL. If you are weighing the two options, the hls4ml tutorial is the best place to see what the tool can and cannot do.

Setup

Hardware

  • Arty A7-100T Artix-7 FPGA development board (part XC7A100TCSG324-1)
  • A host computer running Windows or GNU/Linux
  • A USB-A to Micro-USB cable, for programming the bitstream and for the UART link

Software

  • Vivado Design Suite 2020.1 (including Vivado HLS), available here
  • The Python environment described in the repository’s environment.yml:
conda env create -f environment.yml
conda activate neural-network-fpga

Background

Why FPGAs for inference?

At the heart of a neural network are huge numbers of multiply-accumulate (MAC) operations. Because the output is statistical anyway, inference tolerates reduced numeric precision as long as the final accuracy stays acceptable. Data widths can often drop to 8-bit integers, and sometimes to a single bit. FPGAs can be configured for almost any data width with little loss in compute utilization, which makes them a natural fit.

Compared with other targets:

Platform Strength Weakness
ASIC Highest performance, lowest cost Fixed function, no flexibility
CPU Most flexible to program Lowest compute throughput
GPU High throughput with large batches Needs batching, which latency-critical systems often can’t do
FPGA Low latency on a single query Longer, hardware-oriented development flow

In real-time systems you often can’t wait to fill a batch. FPGAs can be optimized for a single query while still keeping their compute resources busy. When no ASIC exists for the job, that makes them ideal for latency-critical neural network processing.

High-Level Synthesis (HLS)

High-level synthesis (also called C synthesis or behavioral synthesis) takes an untimed description of an algorithm, written in C/C++, and generates a register-transfer level (RTL) design that implements it.

Why use it?

  • Productivity: lower design complexity and faster simulation
  • Portability: one source, many implementations
  • Quality: faster design-space exploration, which leads to better designs

HLS maps software constructs onto hardware like this:

C/C++ construct RTL component
Functions Modules
Arguments Input/output ports
Operators Functional units
Scalars Wires or registers
Arrays Memories
Control flow Control logic

The main steps inside the tool are:

  • Scheduling: inserts clock boundaries into the untimed (or partially timed) input description.
  • Pipelining: starts new loop iterations before earlier ones finish, so multiple iterations run concurrently on the same hardware.
  • Binding: maps operations, variables, and data transfers onto the available hardware resources.

In practice the workflow looks like this:

  1. Define the inputs and outputs. They become the arguments of the HLS top-level function.
  2. Write the C++ and test it in software.
  3. Synthesize it to RTL, then tune the directives until it meets your performance goals within the device’s resources.
  4. Test the synthesized design (C/RTL co-simulation).
  5. Export it as a Vivado IP core and integrate it in a Vivado project for the real FPGA.

hls4ml automates steps 1–3 for neural networks.

The model

Dataset

I used the hls4ml LHC jet tagging dataset (hls4ml_lhc_jets_hlf on OpenML). It contains 830,000 particle jets, each described by 16 high-level features and labelled as one of 5 classes: gluon (g), light quark (q), top quark (t), W boson (w), or Z boson (z). It is a realistic task where very low latency matters, since trigger systems at particle colliders must decide in microseconds.

The labels are one-hot encoded, the data is split 80/20 into training and test sets, and the features are standardized with a StandardScaler.

Architecture

A compact fully connected network:

Layer Units Activation Parameters
fc1 64 ReLU 1,088
fc2 32 ReLU 2,080
fc3 32 ReLU 1,056
output 5 Softmax 165
Total     4,389 
model = Sequential()
model.add(Dense(64, input_shape=(16,), name='fc1', kernel_initializer='lecun_uniform', kernel_regularizer=l1(0.0001)))
model.add(Activation('relu', name='relu1'))
model.add(Dense(32, name='fc2', kernel_initializer='lecun_uniform', kernel_regularizer=l1(0.0001)))
model.add(Activation('relu', name='relu2'))
model.add(Dense(32, name='fc3', kernel_initializer='lecun_uniform', kernel_regularizer=l1(0.0001)))
model.add(Activation('relu', name='relu3'))
model.add(Dense(5, name='output', kernel_initializer='lecun_uniform', kernel_regularizer=l1(0.0001)))
model.add(Activation('softmax', name='softmax'))

The model is trained for 30 epochs with Adam, categorical cross-entropy loss, a batch size of 1024, and a learning-rate-decay callback. On the test set it reaches 76.4% accuracy in floating point.

Converting to firmware with hls4ml

hls4ml is driven by a configuration dictionary generated from the Keras model. Two settings matter most:

import hls4ml

config = hls4ml.utils.config_from_keras_model(model, granularity='name')
config['Model']['ReuseFactor'] = 32
config['Model']['Strategy'] = 'Resource'
config['LayerName']['fc1_input']['Precision'] = 'ap_fixed<8,3>'

hls_model = hls4ml.converters.convert_from_keras_model(
    model, hls_config=config, output_dir='NeuralNetworkModel_1/hls4ml_prj', part='xc7a100tcsg324-1'
)
  • Precision: weights and activations default to ap_fixed<16,6> (16 bits, 6 of them integer). The input layer uses ap_fixed<8,3>, so each of the 16 input features is exactly one byte. That choice makes the UART interface below much simpler.
  • ReuseFactor = 32 with the Resource strategy: each hardware multiplier is reused 32 times per inference. This trades latency for area. A reuse factor of 1 would need one DSP per multiplication, far more than the 240 DSPs on this device.

Before synthesizing, hls_model.compile() and hls_model.predict() run a bit-accurate emulation of the firmware on the CPU, so you can check what the fixed-point conversion costs:

Model Test accuracy
Keras (floating point) 76.4%
hls4ml (fixed point) 74.9%

A 1.5-point drop in exchange for 8- and 16-bit arithmetic is a good deal.

Synthesis results

Running hls_model.build(csim=True) invokes Vivado HLS. The C-synthesis report for the xc7a100t part:

Metric Value
Latency (best / worst) 174 / 178 cycles
Initiation interval 32 cycles
Target / estimated clock period 5.00 ns / 5.92 ns

And the estimated resource usage:

Resource Used Available Utilization
LUT 38,067 63,400 60.0%
DSP48 137 240 57.1%
BRAM_18K 66 270 24.4%
FF 21,654 126,800 17.1%

The DSP count is a nice sanity check. The dense layers perform 16×64 + 64×32 + 32×32 + 32×5 = 4,256 multiplications per inference. With a reuse factor of 32 that is 4,256 / 32 = 133 DSPs, plus a handful for the softmax, which matches the 137 reported.

Note that the estimated clock period (5.92 ns) misses the 5 ns target. The top-level design runs the core from the board’s 100 MHz clock (10 ns period), which leaves plenty of margin. At that clock one inference takes about 1.8 µs.

System integration

The generated IP still has to get data in and results out. I wrote that part in VHDL:

UART

The host talks to the board over the Arty’s USB-UART bridge. Both directions use the standard 8N1 frame (one start bit, eight data bits, one stop bit). A simple baud-rate generator divides the 100 MHz clock by 868, which gives ≈115,200 baud. Transmitter and receiver are each a small state machine that steps through the start bit, the eight data bits, and the stop bit.

FIFO

FIFO stands for First In, First Out. FIFOs are one of the basic building blocks of FPGA and ASIC design, used for:

  • Crossing clock domains
  • Buffering data before sending it off-chip (e.g. to DRAM or SRAM)
  • Buffering data for software to read later
  • Storing data for later processing

Think of a FIFO as a one-way tunnel with a toll gate at the exit. Cars (data words) enter at one end and leave in the same order when the gate opens. If the gate never opens and cars keep coming, the tunnel fills up: that’s a FIFO overflow, and it’s generally bad news. The tunnel’s length is the FIFO’s depth (how many words it can hold). Its number of lanes is the width (bits per word).

In this design the FIFO is 8 bits wide and 16 words deep, which matches the network input exactly. The UART delivers one byte per feature, the FIFO collects 16 of them, and its full contents are exposed as one 128-bit vector that feeds the fc1_input port of the hls4ml core.

Block-level handshake: ap_ctrl_chain

Vivado HLS wraps the core in a block-level control protocol. With ap_ctrl_chain, the core asserts ap_done when a transaction finishes. It only starts the next one immediately if ap_continue is also high; otherwise it halts until ap_continue is asserted. This gives the downstream logic, here the UART transmitter, a way to apply back-pressure.

Takeaways

  • hls4ml removes most of the hard work. Going from a trained Keras model to a synthesizable IP core takes a few lines of Python. Most of the effort moves to choosing precision and reuse factor.
  • Bit-accurate emulation is the key feature. You see the accuracy cost of fixed-point arithmetic before spending any time in synthesis.
  • ReuseFactor is your main area/latency knob. Multiplications ÷ ReuseFactor gives you a good first estimate of DSP usage.
  • Design the I/O around the data types. Choosing an 8-bit input precision made the UART-to-network path a simple byte FIFO.
