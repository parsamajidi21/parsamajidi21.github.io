> **TL;DR**: On the i.MX95, the first instruction does not run on the Cortex-A55. The **PMIC** brings up the rails in a fixed order and releases **POR_B**, then the **BootROM** starts on the **Cortex-M33**. It works from on-chip RAM, reads the boot-mode pins and fuses, brings up the boot device and reads the first container, which holds the firmware for the **EdgeLock Secure Enclave (ELE)**. None of this prints anything, so debugging this stage means knowing what to measure.

## About this series

Most embedded Linux engineers know the boot flow as "U-Boot, then the kernel". On a modern SoC like the NXP **i.MX95**, at least five pieces of firmware run before U-Boot proper, on three different processors, and a dead board can fail in any of them. This series follows the boot from power-on to Linux PID 1, one stage per post, with an animated diagram for each stage.

## Four processors, one boot core

The i.MX95 has more than one kind of processor, and it matters which one starts first:

| Processor                         | Role                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------- |
| **Cortex-M33**                    | Runs the BootROM, then the OEI, then the System Manager for the whole uptime  |
| **Cortex-A55** cluster            | Application cores: SPL, TF-A, U-Boot, Linux. Up to six, depending on the part |
| **Cortex-M7**                     | Optional real-time core, for your own firmware                                |
| **EdgeLock Secure Enclave (ELE)** | Separate security subsystem: keys, fuses, signature checks, crypto            |

The M33 is the boot core because it is also the **system controller**. After the boot it runs NXP's System Manager, which owns power domains, clocks, resets and the PMIC, and serves requests from Linux over SCMI (part 4). The A55 cluster can be powered off completely while the M33 keeps running. The most privileged software therefore runs on the core that is always on, and the application cores start much later, as clients.

If you come from the **i.MX8M** family, this is the big change: there, the BootROM runs on Cortex-A53 core 0, and the M4/M7 is an optional extra. The i.MX95 is closer to the i.MX8QXP, where the ROM ran on a dedicated system controller, except that the i.MX95's System Manager is open source.

## Before the first instruction: the PMIC

Nothing runs until the power rails are up. A **PMIC** (power management IC) takes the input supply and generates every rail on the board. Its **OTP** (one-time-programmable memory) holds the power-up sequence: which rails turn on, in which order, at what voltage, and with what delay between them. NXP pairs the i.MX95 with its own PMICs (the EVK uses a PF09 main PMIC plus PF53 regulators **[VERIFY]**), but the principle is the same on any board.

The rails fall into two groups:

| Rail         | Feeds                   | Typical value                                           |
| ------------ | ----------------------- | ------------------------------------------------------- |
| VDD_SOC      | SoC logic               | depends on the drive mode, about 0.8–0.9 V **[VERIFY]** |
| NVCC 1.8 V   | I/O banks, analog       | 1.8 V                                                   |
| VDD_ARM      | A55 cluster             | separate, so it can be scaled or switched off           |
| LPDDR5 VDD1  | DRAM core, high voltage | 1.8 V                                                   |
| LPDDR5 VDD2H | DRAM core               | 1.05 V                                                  |
| LPDDR5 VDDQ  | DRAM I/O                | 0.5 V                                                   |

The LPDDR5 values come from JEDEC JESD209-5. Some designs also have a separate **VDD2L** (0.9 V) rail; others tie it to VDD2H **[VERIFY for your board]**.

The order matters for two reasons. The SoC datasheet defines a required power-up sequence: powering an I/O bank before the core logic, for example, can drive current through protection diodes into an unpowered domain. LPDDR5 has its own rule: VDD1 has to ramp up before (or together with) VDD2H, and VDDQ comes last **[VERIFY against the JESD209-5 power-up table]**. The PMIC OTP encodes both.

When every rail is in regulation, the PMIC waits a programmed delay and releases **POR_B**, the SoC's power-on reset. Two things happen on that edge: the SoC leaves reset, and the **BOOT_MODE pins are latched**. Changing the boot switches after this has no effect until the next reset.

Note that the LPDDR5 is **powered but unusable** from here on. It holds nothing, and the DDR controller can't talk to it reliably until the link has been trained. That happens in the OEI, two stages later (part 3). Until then, every byte of code and data lives in on-chip RAM.

## The BootROM

The **BootROM** is mask ROM inside the SoC. It is fixed in silicon and can't be updated; fuses can only adjust what it does. Out of reset, the **Cortex-M33** fetches its first instruction from it. The A55 cluster and the M7 stay in reset.

The ROM's world is small:

- **Code** runs from ROM.
- **Working memory** is on-chip **OCRAM**: the stack, buffers, and the image headers it reads. DDR is off limits.
- **It prints nothing.** There is no UART output from the ROM. The first console line on an i.MX95 comes from much later firmware (the OEI built with debug output, or the System Manager **[VERIFY which comes first on your BSP]**).

At the same time, the **ELE** comes out of reset and runs its own internal ROM **[VERIFY]**. The two ROMs talk through a messaging unit (MU). The ELE can't do much yet: its full firmware is loaded by the M33 ROM from the first container, which is the last step of this post and the start of part 2.

## Boot modes

The ROM's first decision is where to boot from. It has two inputs:

- **BOOT_MODE pins**: four pins **[VERIFY count]**, usually wired to a DIP switch on development boards, latched at POR.
- **Boot fuses**: in the OCOTP fuse block. They select the boot device and its parameters (bus width, speed, which controller instance), and can lock the configuration down.

The pins choose between three kinds of mode:

1. **Boot from fuses.** The pins defer to the fuses. This is the normal setting for production hardware: the boot device is fixed in silicon, and a stray switch setting can't change it.
2. **Internal boot from a named device.** The pins select SD, eMMC or FlexSPI directly, overriding the fuses. Convenient during development.
3. **Serial download.** The ROM ignores the boot media and waits for an image over USB.

The exact pin encodings are in the boot chapter of the i.MX95 Reference Manual and in your board's documentation **[VERIFY: table]**. Don't copy switch settings from another i.MX: the i.MX93 and i.MX8M encodings are different.

The ROM's search is also more than one try. NXP describes primary, secondary, recovery and serial download stages **[VERIFY in the RM]**: if the primary image fails, the ROM can try a **secondary image set**, if the fuses configure one, then a recovery device, and finally falls back to serial download.

## Boot devices: where the ROM reads

Once the device is chosen, the ROM brings up its controller and reads the first container header at a fixed location. That location differs per device:

| Device      | Controller | Where `flash.bin` starts                                         | Writing it                                                    |
| ----------- | ---------- | ---------------------------------------------------------------- | ------------------------------------------------------------- |
| SD card     | uSDHC      | **32 KiB** from the start of the card                            | `dd if=flash.bin of=/dev/sdX bs=1k seek=32 conv=fsync`        |
| eMMC        | uSDHC      | offset 0 of the **boot0** hardware partition                     | `uuu -b emmc flash.bin`, or from U-Boot after `mmc dev <n> 1` |
| FlexSPI NOR | FlexSPI    | after the FlexSPI configuration block (FCB) **[VERIFY offsets]** | `uuu -b qspi flash.bin` **[VERIFY]**                          |

Each layout has a reason:

- **SD at 32 KiB** leaves room for the partition table. A GPT with the usual 128 entries occupies LBA 0–33, which is 17 KiB with 512-byte sectors. 32 KiB clears it, and the first real partition starts well after `flash.bin` (often at a few MiB).
- **eMMC boot0** is a separate hardware partition, outside the user area that holds your partition table. Nothing else lives there, so the image can start at offset 0. It also survives a reflash of the user area.
- **FlexSPI** has no standard way to discover how to talk to the chip, so the ROM first reads an **FCB** in a slow, safe mode. The FCB tells it the read command, dummy cycles and clock for that particular NOR flash.

For SD, the ROM starts the card in identification mode at **≤ 400 kHz**, as the SD specification requires, before it switches to a faster bus mode. If you put a scope on SD_CLK you can see this.

## Serial download and uuu

Serial download is how you recover a board with an empty or broken boot device. The ROM gets into it in two ways: the BOOT_MODE pins select it, or it falls back to it after every boot device has failed **[VERIFY: fallback conditions on i.MX95]**.

In serial download mode, the ROM enumerates on the USB OTG port as a USB device with NXP's vendor ID, `1fc9` (the product ID is specific to the SoC; `015d` has been reported for the i.MX95 **[VERIFY]**). On the host, NXP's **`uuu`** (Universal Update Utility) talks to it with the SDP protocol:

```bash
# Linux host: install udev rules once, so uuu doesn't need root
uuu -udev | sudo tee /etc/udev/rules.d/70-uuu.rules
sudo udevadm control --reload

# Is the ROM waiting?
lsusb | grep -i 1fc9

# Boot flash.bin from RAM, without writing anything
uuu flash.bin

# Write the bootloader to eMMC boot0
uuu -b emmc flash.bin

# Write the bootloader and a full disk image
uuu -b emmc_all flash.bin core-image.wic
```

Plain `uuu flash.bin` is useful on its own: it boots your bootloader without touching the board's storage, which is the quickest way to test a new `flash.bin`.

## What this means when you debug a real board

Everything in this post happens before the first character on any UART. A board that stays silent can be stuck anywhere from the PMIC to the ELE firmware, so work from the bottom up and measure instead of guessing:

| Symptom                                                               | Likely stage                 | Check                                                                                                                               |
| --------------------------------------------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| One or more rails missing or wrong                                    | PMIC                         | Measure every rail at its test point; read the PMIC fault registers over I²C if you can                                             |
| Rails fine, POR_B stays low                                           | PMIC / reset circuit         | A rail just outside its power-good window, a supervisor holding reset, a short on POR_B                                             |
| POR_B high, SD_CLK never toggles, nothing on USB                      | Boot mode                    | Switch settings (remember: latched at POR), boot fuses, wrong device selected                                                       |
| SD_CLK toggles briefly, then the board appears in `lsusb` as `1fc9:…` | ROM found no valid container | `flash.bin` written at the wrong offset (forgot `seek=32`), a blank card, or an image built for a different board                   |
| Board in serial download mode doesn't appear in `lsusb`               | USB / host                   | Wrong USB port (it must be the OTG port), cable without data lines, `dmesg` on the host                                             |
| ROM reads the card, nothing ever prints, no USB fallback              | Container #1 / ELE           | ELE firmware for the wrong silicon revision: `mx95a0-ahab-container.img` on B0 silicon or the reverse. Check the marking on the SoC |

The last row is easy to hit: the U-Boot documentation for the i.MX95 EVK lists separate ELE containers for A0 and B0 silicon, and an image built for one revision doesn't boot on the other.

Two habits save time at this stage. First, keep a known-good SD card around: if it boots, the hardware up to the ROM is fine, and the problem is in your image. Second, when you bring up a new board, scope the rails and POR_B once at power-on and save the trace. When a later board revision fails to boot, you have something to compare against.
