> **TL;DR**: On the i.MX95, the first instruction does not run on the Cortex-A55. The **PMIC** brings up the rails in a fixed order and releases **POR_B**, then the **BootROM** starts on the **Cortex-M33**. It works from on-chip RAM, reads the boot-mode pins and fuses, brings up the boot device and reads the first container, which holds the firmware for the **EdgeLock Secure Enclave (ELE)**. On a typical BSP none of this prints to a console, so debugging this stage means knowing what to measure.

## About this series

Most embedded Linux engineers know the boot flow as "U-Boot, then the kernel". On a modern SoC like the NXP **i.MX95**, at least five pieces of firmware run before U-Boot proper, on three different processors, and a dead board can fail in any of them. This series follows the boot from power-on to Linux PID 1, one stage per post, with an animated diagram for each stage.

| 2     | Containers and the Secure Enclave: AHAB, the ELE, `flash.bin`             |

The board in the diagrams is a generic i.MX95 board with LPDDR5, an SD card slot and eMMC, close to NXP's 19 × 19 mm EVK. Where a detail depends on the silicon revision (A0/A1 vs B0) or the BSP version, I say so. I checked the facts here against public sources: the i.MX 95 industrial datasheet (IMX95IEC, Rev. 8), NXP's board guides, the U-Boot documentation and the source code of `imx-mkimage`, `imx-oei`, NXP's U-Boot and `uuu`. I have **not** checked them against the i.MX 95 Reference Manual, which NXP distributes under NDA. Items marked **[VERIFY]** are ones those public sources don't settle.

## Four processors, one boot core

The i.MX95 has more than one kind of processor, and it matters which one starts first:

| Processor                         | Role                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------- |
| **Cortex-M33**                    | Runs the BootROM, then the OEI, then the System Manager                       |
| **Cortex-A55** cluster            | Application cores: SPL, TF-A, U-Boot, Linux. Up to six, depending on the part |
| **Cortex-M7**                     | Optional real-time core, for your own firmware                                |
| **EdgeLock Secure Enclave (ELE)** | Separate security subsystem: keys, fuses, signature checks, crypto            |

The M33 is the boot core because it is also the **system controller**. The datasheet calls this boot type _Low Power Boot_: only the M33 runs after POR. The firmware on the M33 is not one continuous image, though. It runs three separate stages, each with its own job:

1. The **BootROM**, in mask ROM. It picks the boot device and loads and authenticates the images.
2. The **OEI** (Optional Executable Image). The ROM loads it, branches to it, and gets control back when it returns. NXP's `imx-oei` README describes it as configuring "DDR config, init TCM ECC, etc."; on the i.MX95 that means DDR initialization and training (part 3).
3. The **System Manager** (SM). The ROM loads it from the same container. It owns power domains, clocks, resets and the PMIC, and serves requests from the A55 side over SCMI (part 4).

In NXP's BSP the System Manager stays resident: the A55 cluster can be powered off while the M33 keeps running it. That is a property of the SM firmware and the system design, not of the silicon, so a custom design could do something else with the M33. The point stands for the standard flow: the most privileged software runs on the core that boots first, and the application cores start later, as clients.

If you come from the **i.MX8M** family, this is the big change: there, the BootROM runs on Cortex-A53 core 0, and the M4/M7 is an optional extra. The i.MX95 is closer to the i.MX8QXP, where the ROM ran on a dedicated system controller, except that the i.MX95's System Manager is open source.

## Before the first instruction: the PMIC

Nothing runs until the power rails are up. A **PMIC** (power management IC) takes the input supply and generates every rail on the board. Its **OTP** (one-time-programmable memory) holds the power-up sequence: which rails turn on, in which order, at what voltage, and with what delay between them. NXP's reference power architecture pairs the i.MX95 with a **PF09** main PMIC, which sequences the rails, and **PF53** regulators for the high-current VDD_SOC and VDD_ARM rails. NXP's PF09 design guidelines (AN14910) describe that split, and the FRDM i.MX 95 Pro manual shows it on a real board (PF09 plus a PF5302 for VDD_SOC). I have not checked the EVK schematic itself **[VERIFY for the 19 × 19 EVK]**. Other boards may use other PMICs; the principle is the same.

The SoC-side rails, with the typical values from the datasheet's operating-ranges table:

| SoC rail       | Feeds                                 | Typical value (datasheet)                                              |
| -------------- | ------------------------------------- | ---------------------------------------------------------------------- |
| NVCC_BBSM_1P8  | Battery-backed domain (BBSM) I/O      | 1.8 V. First on, last off                                              |
| VDD_SOC        | All SoC logic outside the A55 cluster | 0.80 V low drive, 0.85 V nominal, 0.90 V overdrive (0.65 V in suspend) |
| VDD_ARM        | Cortex-A55 cluster                    | same values per drive mode, and it can be switched off                 |
| VDD\_\*\_0P8   | Analog, DRAM PHY digital, PLLs        | 0.8 V                                                                  |
| 1.8 V supplies | Analog, PHYs, PLLs, 1.8 V I/O banks   | 1.8 V                                                                  |
| VDD2H_DDR      | DRAM PHY                              | 1.05 V for LPDDR5 (1.1 V for LPDDR4X)                                  |
| VDDQ_DDR       | DRAM PHY I/O                          | 0.5 V for LPDDR5 (0.6 V for LPDDR4X)                                   |
| 3.3 V supplies | 3.3 V I/O banks, USB PHY              | 3.3 V                                                                  |

Which drive mode a board runs in depends on the part's speed grade and on how the PMIC and the System Manager are configured, so the VDD_SOC you measure is a **board-specific** value. Check your schematic, the PMIC OTP and the SM board configuration rather than assuming 0.85 V. The datasheet also allows voltages above typ × 1.05 only with a PMIC that supports automatic voltage positioning.

The DRAM chip has its own rails, defined by JEDEC JESD209-5 and the memory vendor's datasheet: **VDD1** (1.8 V), **VDD2H** (1.05 V), **VDD2L** (0.9 V) and **VDDQ** (0.5 V). On most boards the DRAM's VDD2H and VDDQ share the PMIC outputs that feed the SoC's VDD2H_DDR and VDDQ_DDR. VDD1 has no SoC counterpart, and whether VDD2L is a separate rail or tied to VDD2H depends on the memory part **[VERIFY for your board]**.

The order matters because powering one domain before another can drive current through protection diodes into an unpowered domain, or leave a block in an undefined state. The datasheet's power-up sequence for the i.MX 95, in short:

1. NVCC_BBSM_1P8. The SoC then asserts PMIC_ON_REQ.
2. VDD_SOC, then VDD_ARM, together with VDD_SOC or after it. There is no ordering requirement between the two.
3. The 0.8 V analog, DDR, PHY and PLL supplies, which may come up with VDD_SOC/VDD_ARM.
4. The remaining 1.8 V supplies.
5. DDR VDD2H, then DDR VDDQ. The SoC has no requirement between these two, but the DRAM generally needs VDDQ after VDD2H.
6. The 3.3 V supplies (may overlap with step 5), then NVCC_SD2 if it is switched between 1.8 V and 3.3 V for the SD card.
7. POR_B release. POR_B stays asserted for the whole sequence.

The DRAM's own rule for VDD1 relative to VDD2H and VDDQ is in JESD209-5 and the memory datasheet **[VERIFY for your memory part]**. The PMIC OTP has to satisfy both sets of rules.

When every rail is in regulation, the PMIC releases **POR_B**, the SoC's power-on reset, and the SoC leaves reset. According to the datasheet, the hardware samples the **BOOT_MODE pins** before the ROM starts and stores the value in a register, which then holds it. Changing the boot switches after this has no effect until the next reset.

Note that the LPDDR5 is **powered but unusable** from here on. It holds nothing, and the DDR controller can't talk to it reliably until it has been initialized and the link trained. That happens in the OEI (part 3). Until then, every byte of code and data lives in on-chip RAM.

## The BootROM

The **BootROM** is mask ROM inside the SoC. It is fixed in silicon and can't be updated; fuses can only adjust what it does. Out of reset, the **Cortex-M33** fetches its first instruction from it. The A55 cluster and the M7 stay in reset.

The ROM's world is small:

- **Code** runs from ROM.
- **Working memory** is on-chip **OCRAM**: the stack, buffers, and the image headers it reads. DDR is off limits.
- **It prints nothing that I know of.** I have never seen ROM output on a UART, and none of the public NXP material I checked describes any. I can't rule it out without the Reference Manual **[VERIFY]**. Treat the ROM as silent.

Which console prints first depends on the BSP and on how each firmware was built:

| Stage                            | Console          | Prints when                                                                   |
| -------------------------------- | ---------------- | ----------------------------------------------------------------------------- |
| BootROM                          | none known       | see above                                                                     |
| OEI                              | M33 debug UART   | built with debug output (the U-Boot EVK instructions build it with `DEBUG=1`) |
| System Manager                   | M33 debug UART   | by default in NXP's EVK configuration; it also has a debug monitor            |
| SPL, TF-A, OP-TEE, U-Boot, Linux | A55 console UART | depends on each one's console configuration                                   |

On NXP's 19 × 19 EVK the debug USB port exposes four UARTs; the getting-started guide names the third as the A55 console and the fourth as the M33 console. On your own board, which UART instance and pins each stage uses is set by its build configuration, not by the SoC.

At the same time, the **ELE** comes out of reset and runs its own internal ROM **[VERIFY]**. The two ROMs talk through a messaging unit (MU). The ELE can't do much yet: its full firmware is loaded by the M33 ROM from the first container, which is the last step of this post and the start of part 2.

## Boot modes

The ROM's first decision is where to boot from. It has two inputs:

- **BOOT_MODE[3:0]**: four pins, sampled at reset. They are multiplexed with other functions, so the board has to hold them at the right levels while POR_B is asserted.
- **Boot fuses**: in the fuse block. They select the boot device and its parameters (bus width, speed, which controller instance), and can lock the configuration down.

The datasheet defines three boot modes and the pin encodings (BOOT_MODE3 is "don't care" in all of them):

| BOOT_MODE[3:0] | Mode                     |
| -------------- | ------------------------ |
| `x000`         | Boot from internal fuses |
| `x001`         | Serial download          |
| `x010`         | uSDHC1, 8-bit eMMC 5.1   |
| `x011`         | uSDHC2, 4-bit SD 3.0     |
| `x100`         | FlexSPI serial NOR       |
| `x101`         | FlexSPI serial NAND      |
| `x110`, `x111` | Reserved                 |

1. **Boot from internal fuses.** The fuses alone select the boot device. This is the normal setting for production hardware: the boot device is fixed in silicon, and a stray switch setting can't change it.
2. **Normal boot.** The pins select eMMC, SD, FlexSPI NOR or FlexSPI NAND directly. Convenient during development.
3. **Serial download.** The ROM ignores the boot media and waits for an image over USB.

How these four signals reach a switch is a **board** decision. NXP's 19 × 19 EVK uses a four-position switch, SW7. The FRDM i.MX 95 board brings out only BOOT_MODE1 and BOOT_MODE0 on a two-position switch, SW1, and its table lists only serial download, eMMC and SD. Read your board's documentation for the switch-to-pin mapping and the ON/OFF polarity. Don't copy switch settings from another i.MX either: the i.MX93 and i.MX8M encodings are different.

The datasheet also separates three kinds of boot device, which are easy to mix up:

- **Primary boot device**: the one selected by the pins, or by the fuses in internal-fuse mode. Valid options are SD, eMMC, FlexSPI NOR and FlexSPI NAND, subject to other fuse settings.
- **Recovery boot device**: if booting from the primary device fails, the ROM tries another source. The datasheet says the recovery device can only be on **SPI1 or SPI2**. Whether recovery is enabled, and how the device is configured, is set by fuses **[VERIFY in the RM]**.
- **Serial download device**: USB1 or USB2.

Within the primary device the ROM can also try a **secondary image set**, if the fuses configure one, before it moves on **[VERIFY in the RM]**. What happens after both the primary and the recovery device fail, and the fuses that change or disable that behaviour, are described in the System Boot chapter of the Reference Manual, which I haven't checked. Don't assume the ROM always ends up in USB serial download (see below).

## Boot devices: where the ROM reads

Once the device is chosen, the ROM brings up its controller and reads the first container header at a fixed location. That location differs per device. The table shows the layouts that NXP's tools produce for the primary image set:

| Device      | Controller            | Where the image starts                                         | Writing it                                                    |
| ----------- | --------------------- | -------------------------------------------------------------- | ------------------------------------------------------------- |
| SD card     | uSDHC (uSDHC2 on EVK) | `flash.bin` at **32 KiB** from the start of the card           | `dd if=flash.bin of=/dev/sdX bs=1k seek=32 conv=fsync`        |
| eMMC        | uSDHC1 only           | `flash.bin` at offset 0 of the **boot0** hardware partition    | `uuu -b emmc flash.bin`, or from U-Boot after `mmc dev <n> 1` |
| FlexSPI NOR | FlexSPI               | FCB at **1 KiB**, first container at **4 KiB** (FlexSPI build) | `uuu -b qspi <flexspi image>`, or `sf write` from U-Boot      |

Sources: the U-Boot i.MX95 EVK documentation gives the SD command. NXP's U-Boot fastboot code uses offset 0 on eMMC boot0 and 0x8000 (32 KiB) on SD for i.MX9 parts. The FlexSPI offsets come from `imx-mkimage`'s `iMX95/soc.mak`, which writes the FCB at 1 KiB and states that the first container is at 0x1000 for FlexSPI boot. These offsets belong to this image format and the default (primary-set) fuse configuration. A secondary image set, a different `imx-mkimage` target or different boot fuses can move them, so check your layout against your build.

Each layout has a reason:

- **SD at 32 KiB** leaves room for the partition table. A GPT with the usual 128 entries occupies LBA 0–33, which is 17 KiB with 512-byte sectors. 32 KiB clears it, and the first real partition starts well after `flash.bin` (often at a few MiB).
- **eMMC boot0** is a separate hardware partition, outside the user area that holds your partition table. Nothing else lives there, so the image can start at offset 0. It also survives a reflash of the user area.
- **FlexSPI** has no single way to talk to every NOR chip, so the ROM first reads an **FCB** with conservative default settings. The FCB tells it the read command, dummy cycles and clock for that particular flash. The FlexSPI image is a separate build (`make flash_a55_flexspi` in `imx-mkimage`, which generates and inserts the FCB), so you can't write the SD `flash.bin` to NOR and expect it to boot. The exact default settings the ROM uses for the first read are in the Reference Manual **[VERIFY]**.

For SD, the ROM starts the card in identification mode at **≤ 400 kHz**, as the SD specification requires, before it switches to a faster bus mode. If you put a scope on SD_CLK you can see this.

## Serial download and uuu

Serial download is how you recover a board with an empty or broken boot device. The reliable way into it is to **select it with the BOOT_MODE pins** (`x001`). The ROM may also end up there when the primary and recovery boot fail, but whether it does depends on the fuse configuration, and secure-boot fuses can restrict serial download. I haven't confirmed the exact conditions **[VERIFY in the RM]**. On a board that looks dead, set the switches to serial download rather than waiting for a fallback.

The datasheet lists USB1 and USB2 as serial download ports. On NXP's boards the documented port is USB1, and the FRDM i.MX 95 Pro manual says that serial download is enabled on USB1 only by default. In serial download mode the ROM enumerates as a USB device with NXP's vendor ID, `1fc9`. `uuu`'s source code lists two product IDs for the i.MX95, `015d` and `015c`, both using the SDPS (stream) protocol. It doesn't say which silicon revision or configuration uses which **[VERIFY with `lsusb` on your board]**. On the host, NXP's **`uuu`** (Universal Update Utility) talks to the ROM:

```bash
# Linux host: install udev rules once, so uuu doesn't need root
uuu -udev | sudo tee /etc/udev/rules.d/70-uuu.rules
sudo udevadm control --reload

# Is the ROM waiting? Expect 1fc9:015d or 1fc9:015c
lsusb | grep -i 1fc9

# 1. Boot flash.bin into RAM, without writing anything
uuu flash.bin

# 2. Write flash.bin to the eMMC boot0 partition
uuu -b emmc flash.bin

# 3. Write a disk image to the eMMC user area, and flash.bin to boot0
uuu -b emmc_all flash.bin core-image.wic

# Show what a built-in script really does on your uuu version
uuu -bshow emmc
```

These are three different operations:

1. **Boot into RAM.** `uuu flash.bin` streams the image to the ROM, then to SPL, and nothing on the board's storage changes. This is the quickest way to test a new `flash.bin`. The hand-off from the ROM to SPL uses uuu's SDPV protocol, which NXP's BSP builds of SPL support; I haven't tested this with an upstream U-Boot build **[VERIFY]**.
2. **Program eMMC boot0.** The built-in `emmc` script boots `flash.bin` the same way, then uses fastboot in the running U-Boot to write it to the `bootloader` target. NXP's U-Boot maps that target to offset 0 of boot0 on i.MX9 parts. The script then runs `mmc partconf` to make boot0 the eMMC's boot partition. This needs a U-Boot with fastboot support, which NXP's BSP images have.
3. **Program the user area.** The built-in `emmc_all` script writes the `.wic` image to the eMMC user area (your partition table and root filesystem), then writes `flash.bin` to boot0 as above.

I checked these against the built-in scripts in the current `mfgtools` source. The scripts change between releases, so run `uuu -bshow <script>` to check yours. For SD cards, NXP's getting-started guides use the `sd_all` script instead.

## What this means when you debug a real board

Everything in this post happens before the first character on any UART. A board that stays silent can be stuck anywhere from the PMIC to the ELE firmware, so work from the bottom up and measure instead of guessing. Each symptom below has more than one possible cause, so treat the table as a list of places to look first:

| Symptom                                                         | Possible causes                                                                                                                                                                                     | Check                                                                                                                   |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| One or more rails missing or wrong                              | PMIC OTP or configuration, a fault the PMIC latched, an overloaded or shorted rail                                                                                                                  | Measure every rail at its test point and compare with your schematic; read the PMIC fault registers over I²C if you can |
| Rails fine, POR_B stays low                                     | A rail just outside its power-good window, a supervisor holding reset, a short on POR_B, a missing pull-up (POR_B has no internal one)                                                              | Scope POR_B against the rails; check the reset circuit                                                                  |
| POR_B high, SD_CLK never toggles                                | Boot mode or fuses select another device, the ROM is booting from or waiting on another interface, NVCC_SD2 or card power missing, a fault before the ROM reaches the SD controller                 | Switch settings (sampled at reset), boot fuses, `lsusb` on the host, SD power rails; probe the other boot interfaces    |
| SD_CLK toggles, then the board appears in `lsusb` as `1fc9:…`   | No valid image found on the card: wrong offset (forgot `seek=32`), a blank card, an image for another board or boot device                                                                          | Dump the first ~1 MiB of the card and look for the container at 32 KiB; rebuild for the right target                    |
| Board in serial download mode doesn't appear in `lsusb`         | Wrong port (use the serial download port, USB1 on NXP's boards), cable without data lines, USB power or PHY supply problem, serial download restricted by fuses                                     | `dmesg` on the host, another cable, the USB rails                                                                       |
| The ROM reads the card, nothing ever prints, no USB enumeration | Among others: ELE firmware for the wrong silicon revision (`mx95a0-ahab-container.img` on B0 or the reverse), an authentication failure, a later stage (OEI, DDR) failing with its debug output off | Check the SoC marking against the container you built; rebuild the OEI with debug output and watch the M33 UART         |

The wrong ELE container is easy to hit: the U-Boot documentation for the i.MX95 EVK lists separate ELE containers for A0 and B0 silicon, and an image built for one revision doesn't boot on the other. But silence after the ROM has read the card has other causes too, which parts 2 and 3 cover.

Two habits save time at this stage. First, keep a known-good SD card around: if it boots, the hardware up to the ROM is fine, and the problem is in your image. Second, when you bring up a new board, scope the rails and POR_B once at power-on and save the trace. When a later board revision fails to boot, you have something to compare against.
